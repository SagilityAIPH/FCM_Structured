## Legacy CEM, in execution order

1. **Import and entry:** `src/fcm_intake/legacy/legacy_cem.py:1-20` imports Selenium and immediately creates a **separate Edge WebDriver** (`EdgeService(executable_path=CONFIG_EDGE_DRIVER_PATH)`, `edgeOptions`, `driver`); this is **not** the CMS IE-mode driver. Options ignore certificate errors, allow insecure localhost and disable popup blocking (`:14-20`). The driver-path setting is `fcm_intake.config.EDGE_DRIVER_PATH` (`:5,19`). Merely importing for the dynamic customer-checker call opens a browser. The actual function is `main(CustomerName, ClaimID, ClaimantName)` (`:274-281`), which title-cases the first input before `employerSearch` (`:276`). `CustomerName` is used as employer name, despite its name; the claim ID and claimant name only reach workbook logging (`:120`). A direct `__main__` example passes **only one argument**, so invoking that script directly raises `TypeError` (`:417-418`). `custSearch()` (`:162`) is defined but never called by `main` or another executable reference found.
2. **Employer search:** `employerSearch` navigates to a **CEM employer-search page** via an inline URL (`:51-52`; repository documentation identifies this as UAT, `docs/code/legacy-code.md:35`). If an optional login button appears, click it (`:54-56`); there is no credential entry or verified login in this module. Sleep 5 seconds (`:57`), write global `EMPLOYER_CODE` and title-cased `CustomerName` in search inputs (`:59-63`), click Search (`:65-66`), sleep 5 (`:68`). The module-level address/code/customer/CASE_NUM globals are initialized at `:22-45`; no caller provides them, and employer address is blank (`:25-30`). `elementExist` waits at most 10 seconds for DOM **presence**, catches everything and returns `False` (`:267-272`); it does not verify a completed search or absence of matching rows.
3. **No results table → Add Employer request:** On absence of the table (`:71-72`), click Add (`:73-75`); enter employer name (`:76`), enter the inline fixed bill-to customer selection and press Return (`:77-80`). This is a hard-coded business choice, not derived from the passed customer or checked for a selected/read-back result. Because `EMPLOYER_ADDRESS1` is blank by default (`:27`), enter `Unknown` street/city, select `Unknown` state, zero ZIP placeholder and `USA` (`:82-100`). If a caller mutates the module globals to supply an address, use `EMPLOYER_ADDRESS1/CITY/STATE/ZIP` and `USA` instead (`:101-117`). Then `notify` asks the operator to **validate and manually click Submit in CEM before clicking OK** (`:119`). The code does **not** click the employer Submit button, confirm submission, capture request ID, or read status. Immediately after the notification returns, it calls `add_claim_record(ClaimantName, ClaimID)` (`:120`), whether or not the operator actually submitted. The *manual* portal Submit is potentially irreversible and may create a request; workbook creation is not proof of submission or CMU completion.
4. **Results table present → employer/location path:** Iterate rows and select any whose first-column text contains `CustomerName`, case-sensitively (`:121-130`); no disambiguation, no break and no explicit no-match outcome. Attempt to inspect location rows (`:132-140`), matching address by substring. `find_elements(By.TAG_NAME, './/tbody/tr')` and `find_element(By.XPATH, '.td[1]')` are suspicious invalid/mismatched selectors (`:133,136`); blank `EMPLOYER_ADDRESS1` would match every address if reached (`:138`). If not found, click Add Location (`:142-145`), fill address/city/state/ZIP/country (`:147-156`) and write `EMPLOYER_ZIP` **rather than `CASE_NUM`** to the case input (`:158-159`). No submit, save, return, confirmation or workbook row in this branch. A table with no matching employer falls off the function silently. A table's mere presence, including an empty table, suppresses Add Employer (`:72`).
5. **Separate dormant customer search:** `custSearch()` navigates to a different **CEM customer-search page** (`:162-163`), optionally clicks login (`:165-168`), searches by `CUSTOMER_NAME` or `CUSTOMER_CODE` globals (`:169-175`), then checks table presence (`:177-180`). No table → click Add Customer, fill `CUSTOMER_NAME`, and if **employer** address is blank fill customer address/city/state/ZIP/country and `CASE_NUM` (`:181-206`); the absence of an else means supplied employer address skips those fields. Table present → case-insensitive name match, click result, optionally filter state, inspect/add a location and fill customer location and `CASE_NUM` (`:207-248`). It obtains a Submit element but its `.click()` is commented out (`:250-251`). The location selectors have the same suspicious TAG_NAME/XPATH issues (`:222,225`); no main-path invocation, result, readback or workbook logging. Do not treat this as live CEM behavior.
6. **Notification, cleanup, errors:** `notify` creates a topmost Tk info box; on any Tk exception it merely prints (`:253-264`), so the manual-submit instruction may cease to be blocking. `main` catches and prints any `Exception` from `employerSearch`, then sleeps 10 seconds and quits `driver` (`:274-281`), returning `None` on both success and failure. A `driver.quit()` error is not caught there. `SystemExit` is not caught by `except Exception`, but **no `sys.exit` call exists in this file** (`sys` is only used for frozen-path detection at `:283-299`). Delays are fixed `sleep(2/5/10)` around actions (`:57,68,75,79,81,100,117,130,145,168,177,183,185,206,216,234,280`); DOM presence wait is the only bounded wait (`:267-272`). No final request ID, portal state or idempotency check.

## Daily workbook contract and reader

- Writer: `legacy_cem.py:289-290,293-314,317-361,364-409`. Filename is **`FCM CEM Checher.xlsx`** (typo is the literal contract); stored beside the source module when running from source, beside `sys.executable` when frozen (`:293-306`). Today's worksheet is `%m%d%Y` (`:309-314`); create file/sheet if missing and enforce row-one headers **Claimant | Claim ID | Status** (`:317-361`). Fill the first wholly empty A/B/C row or append (`:364-382`). `add_claim_record` writes claimant, claim ID, `Status` and saves/closes (`:385-409`). Employer path calls it without Status (`:120`), hence **blank Status**; neither CEM nor any reader sets/updates Status. There is no duplicate check, locking, atomic save, request ID, employer name, submit timestamp or CMU completion marker. Write errors are swallowed by `main` and do not reach its caller.
- Reader: `src/fcm_intake/legacy/CMS.py:1915-1965` independently resolves the **same filename beside its own module / frozen executable**, opens **today's sheet only** (`:1937-1950`), normalizes claimant and claim ID by strip + lowercase, checks exact A/B match (`:1952-1960`), **does not inspect Status (column C)**, returns `False` if workbook/sheet absent. In legacy `CMS.searchCase`, this presence flag selects RRS option **10** instead of **3** (`CMS.py:1858-1883`); this reader does not poll for CMU completion. Source-mode paths happen to coincide because both modules share a directory; packaging as separate executables may point to different folders.
- CMS Registration adapter uses **`CMS.py`'s** reader, not `legacy_cem.py`: `Processes/CMS-Registration/Deploy-Ready/cms_steps.py:43-46,815-842,876-883,916-936`. It checks workbook and current sheet availability before `legacy.claim_exists(full_name, claim_number)`, returning `None` on absent/unreadable/invalid state. `True` means row exists, **not** confirmed employer submission or CMU completion. A readable sheet and no row returns `False`. There is no periodic polling; a new operator-started run performs the check at DATA. If request supplies an explicit boolean, that takes precedence over the loaded hint (`cms_registration_flow.py:61-71`).

## Reuse assessment / tests / risk

- **Wrap safely:** Extract a pure CEM controller with explicit input (employer identity, claimant/claim, optional address, selected bill-to), stage callbacks `search_employer`, `review_match`, `prepare_request`, `confirm_manual_submission`, `record_request` plus `notify`; typed outcomes should distinguish existing match, submitted/verified request, operator cancellation, not-found/ambiguous and failure. The workbook path/date/row/header helpers (`legacy_cem.py:289-409`) can be moved or wrapped behind injected `path`, `today`, and persistence callbacks, with synthetic temporary workbook tests. The CSS/XPath-bound `employerSearch` can only be used as an **attended, isolated adapter** after eliminating import-time driver creation, global `driver`/address values and swallowed errors; unlike the registration adapter (`cms_steps.py:43-65,863-951`), it does not accept an injected driver or return verified step results. The dormant `custSearch` and location branch should not be treated as proven reusable workflows.
- **Rewrite/gate:** Portal selector/row matching and readiness, portal environment choice, bill-to mapping and approval, actual submit ownership, submission readback/idempotency, existing-employer/location decisions, status lifecycle and CMU handoff. A table-presence test is not a verified no-match; a blank row marked in a workbook is not a submitted request. Do not auto-submit or choose production from the legacy inline target. Separate CEM Edge from CMS IE-mode session. Legacy path's browser options weaken certificate checks (`:14-17`). `main` masks errors and always returns `None` (`:274-281`); import-time creation and `driver.quit` make reuse brittle. Potential double-submit on retry after a successful manual action; no request ID or deduplication. Workbook may get a row even when manual submission was skipped and may not be available to CMS Registration packaged separately.
- **Existing tests:** No direct offline behavioral test of `legacy_cem.employerSearch`, `custSearch`, `main`, or its workbook writer found in the searched Python tests. Reopen-Check asserts unresolved/CEM stop (`Processes/Reopen-Check/Stand-Alone/test_flow.py:58-60`) and mocks its prompter for customer outcomes (`:180-218`); Final Code asserts propagation of the stop (`tests/unit/test_final_code_orchestrator.py:103`); package/self-test checks presence/compilation only (`tests/unit/test_final_code_package.py:113`, `Processes/Reopen-Check/Stand-Alone/CMSCustomerSearch.py:42-44`). CMS Registration has synthetic controller/CEM True+unknown tests (`Deploy-Ready/test_flow.py:57,99-106`), workbook hint and live-session fake tests (`Deploy-Ready/test_steps.py:437-522`) and offline scenarios above. These do not demonstrate real CEM portal submission.
- **New synthetic fakes needed:** explicit fake Edge DOM/driver/session factory (navigation, optional login, loading/empty/ambiguous tables, location rows, form fields, dropdown and readback); separate CMS customer prompter fake; operator submission confirmation/cancellation callbacks; deterministic clock and scratch workbook path; fake workbook locked/corrupt/missing/today-sheet cases; save failure, `SystemExit`, browser-cleanup failure, duplicate retry, and false-success after skipped manual submit. Avoid importing the legacy module itself in offline tests until import-time Edge construction is isolated or intercepted.

## Open decisions

1. Is the CEM step only a request prepared for **manual** operator Submit, or should the new module submit automatically after a pre-write review? What portal confirmation/request ID establishes success and prevents duplicate requests?
2. What is the authorized environment and authentication/session source? Legacy CEM uses an inline UAT destination, Edge, and no credential form; CMS search uses IE mode.
3. Are existing-employer/location and customer creation in scope, or only the missing-employer request? What constitutes a true no-match versus an empty/loading table?
4. Who updates `Status`, what are its permitted states and the CMU completion signal? Does downstream registration require request **presence**, submitted confirmation or CMU completion? Where should the shared artifact live for independent executables?
5. How is the bill-to customer selected and verified, and which source supplies employer address/case number? The legacy implementation uses globals/placeholders and an inline fixed customer.
6. Should the current Reopen-Check/Final Code nested live legacy CEM call be replaced by an explicit modular handoff? Keep the business stop and independent post-CMU start separate from any automatic call chain.
