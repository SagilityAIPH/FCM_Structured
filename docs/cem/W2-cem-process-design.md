## 4. Proposed `Processes/CEM/` module (not implemented)

**Boundary/purpose:** Independently operator-started, attended **employer-request creation/linking** from a confirmed unresolved employer in CMS; validate bill-to customer, search CEM for duplicate employer/requests, prepare exact request, require explicit pre-submit review and consent, submit through a controlled live adapter, read back request identity/status, and record an auditable routing receipt. The module is **not** CMS Customer Search, SLB employer typing, Unity employer assignment, CMS case setup, RRS option 10, Outlook sending, or CMU/Data Control approval/completion. A submitted CEM request is `completed` **for the request process only**; keep `request_status='submitted'` separate from `employer_available/approved`. Do not promise that a completed module means the employer exists in CMS. An existing employer missing a customer link and an address add are distinct request kinds; first version should implement `new_employer` only unless BA supplies documented add/link/address rules and portal verification. The CMU team/external Data Control performs approval/add/link and communicates outcome outside the module; a separate status-check/follow-up process could be added later, not an in-process wait.

**Suggested frozen input contract (`Deploy-Ready/contract.py`):**

| Field | Requirement / provenance |
|---|---|
| `employer_name: str` | **Required** reviewed canonical AI `Employer Name` (PDF Customer Name) **or** operator-confirmed name from source document; reject `Not found`, `Not Given/Not Applicable`, blanks. AI special-instructions text is not an authoritative top-level employer name (`AI/referral_schema.py:119-125,163-166`). |
| `claim_number: str`, `claim_id: str`, `claimant_first_name: str`, `claimant_last_name: str` | **Required correlation** from reviewed AI/Final Code fields or explicit operator input; keep claim number separate from PDF Claim ID and CMS Case ID. Whether claimant identity is needed by portal is not proven; needed at least for exact tracking and the current checker legacy bridge. Store sensitive values only in controlled operational tracking, not general logs/fixtures. |
| `customer_name: str = 'Liberty Mutual Commercial Market'`, `customer_code: str = 'C02283'` | **Required confirmed policy and portal lookup** (BRD 111–112), not inferred from `Employer Name` or AI `Company / Market`. Fixed default is a proposal for this Liberty-only flow; require readback of actual bill-to customer and its CMS existence before submitting, or stop. No fallback to invent a customer. |
| `cms_search: SearchEvidence` | **Required**: query/result cardinality or reviewed candidate list, outcome `no_match`/`unlinked`/`ambiguous`, source/time, and selected target evidence. From CMS Customer Search or operator-confirmed recheck; stale/ambiguous evidence goes to review, not blind submit. Exact source IDs must be defined with the predecessor. |
| `request_kind: Literal['new_employer','link_existing','address_add']` | Required discriminator in eventual contract; recommend v1 accepts only `new_employer`, stops unsupported kinds with reason. Existing employer E-code mandatory for `link_existing`; location/address identity mandatory for `address_add`. |
| `address1, address2, city, state, postal_code, country: str` | Optional **in identity contract**, sourced from referral/FROI/supporting document or operator; **conditional required by validated portal/policy**. AI currently has no canonical employer postal address (`docs/cms-registration/W3-cms-registration-data-and-module.md:63`), so operator entry/verification is necessary. Do not silently use legacy `Unknown`/dummy postal values (`legacy_cem.py:82-99`) without explicit BA authorization. |
| `employer_code: str = ''`, `existing_request_reference: str = ''` | Optional only for new employer. For link-existing/address-add require stable employer code/location key; existing request ref suppresses duplicate submission and supports status lookup. |
| `referral_number: str = ''`, `record_id: str = ''`, `cms_case_id: str = ''`, `source_label: str = ''` | Optional correlation only; AI Referral Number is optional (`AI/referral_schema.py:90`); `record_id` is local metadata, and CMS case ID must never be replaced by `claim_id` (`docs/code/data-contracts.md:42-50`). |

Prefer nested frozen `SearchEvidence`, `EmployerAddress`, `CEMRequest`, `CEMReceipt`, `StepResult`, `CEMStages` dataclasses rather than arbitrary dicts. Include a validation method with explicit rejection reasons. The controller should not import Selenium, database, `legacy_cem`, or workbooks on import; lazy live adapter with injected `search_cms_customer`, `search_cem_employer`, `search_existing_requests`, `review`, `confirm_submit`, `submit`, `readback`, `record_receipt` callbacks. Never import the legacy module at controller import time: it opens Edge immediately (`legacy_cem.py:14-20`). Legacy code is a behavioral reference, **not** a trustworthy successful-submit callback.

**Readiness and attended gates:**
1. Desktop opens **idle**; explicit **Start** only, atomically reject double-click/concurrent starts. Form or workbook input must be complete; no portal/network work or browser startup on import/open.
2. Preflight referral eligibility and exact customer C02283/CMS existence, reviewed employer name, unresolved predecessor match, supported request kind, required portal fields, target environment/authentication, and privacy-safe correlation. No claimant/claim cross-match → `stopped/identity_mismatch`.
3. Search CEM employer **and pending requests** by name/code/address/customer link. Exact existing/link or already-pending request → `stopped/already_exists` or `stopped/duplicate_request` with reference; ambiguous names, uncertain link, stale evidence → `stopped/ambiguous_employer`, not new submission. Guard again just before submit (time-of-check/time-of-use; ideally portal-enforced idempotency key).
4. Show portal values including name, bill-to code/link, request kind, address/ZIP and any existing match in an **operator review**; Approve/Cancel. Missing address policy cannot be smuggled through a placeholder. Prompt a distinct **irreversible Submit confirmation**, with request identity/environment. Operator cancellation → `cancelled/operator_cancelled` without submission or routing workbook row.
5. Submit only once. Read back a durable portal request reference or uniquely identified pending-request record and status; never mark `completed` for button click, alert acknowledgement or local row alone. If submit response is uncertain, **stop and reconcile before retry** to avoid duplicate requests. Persist a receipt only after positive readback; report tracking failure distinctly and do not auto-resubmit. No automated CMU wait or approval assertion.

**Result contract:** every result has `outcome` (`completed|stopped|cancelled|failed`), `reason`, `stage`, completed `stages`, `steps`, `request_reference` (empty unless verified), `request_status` (`submitted|pending|rejected|unknown` as observed; never guessed), `employer_code` (if read back), `customer_code`, `cem_workbook_row` (sheet/row or `None`), `tracking_status` (`written|existing|failed|not_attempted`), `problems[]`, and sanitized `error{stage,type,message}|None`. Suggested stages `START → VERIFY_SOURCE → SEARCH → REVIEW → SUBMIT → VERIFY_RECEIPT → TRACK`. `completed/request_submitted` requires readback + tracking write/readback (if tracking is mandatory); `stopped` for invalid request, no supported route, ambiguous/duplicate existing employer/request, unknown prerequisites/policy; `cancelled` for operator refusal; `failed` for portal, readback, or tracking failure. If portal submission succeeded but tracking failed, return `failed/tracking_failed_after_submit` **with the verified request reference and explicit no-retry warning**; do not hide the side effect. Keep CMU completion outside this result.

**Tracking/workbook contract:** Legacy `FCM CEM Checher.xlsx` (`legacy_cem.py:289-409`) is a **routing hint**, not portal proof. Daily date sheet, columns `Claimant`, `Claim ID`, `Status`; `add_claim_record` appends, does not deduplicate or capture a reference, and current CMS checker tests claimant + **claim number** (`cms_steps.py:815-842`). Before adapting it, settle whether column B means PDF `Claim ID` or claim number. Recommend one controlled **request ledger** with immutable request ref, claim number, claim ID, normalized employer + bill-to code, operation, submitted timestamp/environment, status/provenance and optional legacy sheet/row; atomic locked writes, idempotent per portal ref and exact referral identity, text IDs/formula rejection, explicit readback. Do not place full referral/PHI in portable report. Until CMS Registration consumes a structured verified receipt, a compatibility writer may populate the legacy dated sheet **only after portal readback** with the BA-approved key; preserve its existing headers/behavior, do not equate workbook membership with approval. A missing/unreadable sheet is `unknown`, never `False`. Define where the ledger lives and access/retention with the owner; no new shared workbook format silently substituted for existing consumers.

**Deploy-Ready vs Stand-Alone:** `Deploy-Ready/contract.py`, `cem_flow.py` (pure controller), `cem_rules.py` (normalization/duplicate and identity policy), `cem_steps.py` (lazy portal/CMS adapters with injected driver/session); tests with fake callbacks. `Stand-Alone/run.py`, `backend.py`, form/workbook adapter, React/pywebview UI, synthetic JSON scenarios, `--self-test --report`, tests, packaging recipe. Default and all scenario runs are strictly offline; `--live` requires operator Start, approved environment/credentials via approved channel, and separate live authorization. Reuse CMS Registration's distinctions among `completed`, `stopped`, `cancelled`, `failed`, review/confirmation and readback (`Processes/CMS-Registration/Stand-Alone/README.md:3-19`), not its CMS setup logic.

**Offline synthetic scenarios:**
- `request-submitted`: no CMS/CEM employer or pending request, correct C02283, reviewed full address, explicit approvals, submitted reference + pending status and row readback → completed.
- `missing-employer`, `missing-identity`, `bill-to-not-verified`, `address-policy-unknown`, `unsupported-link-or-address` → business stops before portal mutation.
- `existing-employer`, `existing-unlinked-employer`, `ambiguous-name`, `existing-pending-request`/`duplicate-ledger-row`, `stale-search` → no duplicate submit; show candidate/reference for operator.
- `cancel-review`, `decline-submit`, `double-start` → no submit/no phantom tracking.
- `portal-rejects`, `submit-timeout-with-possible-side-effect`, `receipt-missing-or-mismatched`, `tracking-write-fails-after-submission`, `SystemExit`/exception and cleanup → precise failure, no retry without reconciliation; preserve verified ref.
- `legacy-key-mismatch`: synthetic distinct claim number and Claim ID ensure workbook writer/reader cannot silently disagree; `registration-handoff` tests that true/false/unknown CEM status maps to 10/3/stop with explicit operator confirmation.
- Assert no live imports/browser/database on offline run, no real person/claim data, no submission for stops/cancels, and no duplicate submit on replay.

**Integration options and recommendation:**
- **A (recommended):** CEM is its own **attended independent run**. Customer Search emits a structured unresolved handoff; operator starts CEM, then explicitly restarts/resumes intake with a verified receipt; CMS Registration later consumes a verified `cem_employer_request` decision plus receipt/reference, retaining option-10 human confirmation. No module auto-calls the next. This matches current operator-start rule and cross-app human work; requires a designed resumable/placeholder handoff because Final Code currently stops.
- **B:** add an optional attended CEM stage inside Final Code immediately after CMS search while still requiring an explicit separate **Start CEM** and review/submit gates, then resume SLB in memory. Reduces re-entry but couples Final Code to a second portal/session and new partial-failure/resume semantics; not recommended until live CEM policies and Final Code handoff are settled. Neither choice permits silent auto-start after a no-result search. In both options, Unity/CMS case setup should read the request receipt/status and revalidate actual employer availability; registration must not interpret a CEM `completed` receipt as CMU approval or select `3` on an unknown status.
