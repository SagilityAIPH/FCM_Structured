## A. R29 — direct request for the named GAA FCM prohibited

Worse, an explicitly requested nursing-vendor person is treated as the assigned `NCM`, then carried to the RRS Subject Line Builder's Requested NCM selection, without exclusion of the named GAA FCM. This is not proof a live assignment to that individual has occurred; it is a source-level path that can contradict the rule.

**Inputs and availability.** After CAPTURE, complete accessible referral text and attachment name are available (`Final Code/finalcode/orchestrator.py:73-82`); extraction supplies `NCM`, nurse email, Special Instructions, preliminary Employer Name, claimant city, claim and referral type (`AI/referral_schema.py:21-51,106-111,344-450`). Review can correct fields (`Final Code/finalcode/orchestrator.py:84-96`). The exact customer **code** C02283, GAA affiliation of an extracted person, local branch contact, alternative staff availability, alternate FCM identity, award state, notification to Liberty, Liberty's permission and RRS removal status are not represented in that contract. CMS later returns a *resolved employer/customer name*, not a customer code (`Final Code/finalcode/orchestrator.py:98-120`). A separate authoritative identity lookup/mapping and attended decision record would be needed; employer name alone is not the carrier/customer identity.

**Owner and timing.** Recommended owner is an attended Wizard rule at **FIRST** after capture/extraction to flag a likely prohibited request before SLB can set Requested NCM; **MID** after review and verified carrier identity to resolve ambiguity and pause before CMS/SLB or Unity; **LAST** immediately before actual assignment/completion as a guard against proceeding without documented permission. The earliest rule can be provisional if Liberty identity is not verified. Final Code's last boundary is SLB/triage, *not* RRS assignment; standalone Unity owns the last assignment guard.

**Deterministic or AI.** Deterministic matching of the verified carrier code, explicitly identified person, an explicit request, and persisted human permission/alternate-assignment state is the enforcement mechanism. A narrowly scoped AI analysis of ambiguous narrative could propose source spans and uncertainty; it must not infer permission, award, nurse availability or a branch response. Extracted `NCM` alone cannot distinguish historical/assigned nurse from a prohibited direct request (`AI/referral_schema.py:166-172`).

**Violation behaviour candidates — undecided.** Flag a possible direct request with citation for review; pause before `cbReqNCM`/subject-line creation and independently before Unity/RRS assignment; hand off to the local branch with “staffing, not awarded” instructions; resume only on recorded alternate assignment *and* explicit Liberty permission. If denied, human-led decline as nurse unavailable and removal from RRS. Whether the bot should create communications/tasks or perform decline/removal is an owner decision, not existing capability. A simple Yes/No acknowledgement alone must not be confused with evidence of customer permission.

**Gaps, risks, open questions.** Who maintains the prohibited-person list (name variants/vendor identifiers), carrier-code lookup, local-branch contact, and a durable permission/award record? Which party sends and verifies branch/Liberty messages? Does the requested name live exclusively in Special Instructions or attachments that capture can miss? Can RRS reliably remove a referral after a human decline? What does a previously assigned/reopened case mean? Do not auto-select a substitute, auto-award, automatically contact Liberty, auto-decline, or silently remove from RRS. The human negotiation cannot be replaced by model output.

## D. Candidate FIRST / MID / LAST seams

**Final Code** — `Final Code/finalcode/orchestrator.py:15,34-54,73-139` is a fixed synchronous sequence `CAPTURE → EXTRACT → REVIEW → GATE → CMS → SUBJECT LINE BUILDER`; `on_stage` reports stage entry only, not an interstage callback. `Final Code/finalcode/app.py:150-162,165-223` constructs injected capture/extract/review/cms/subject-line callables, stage publication and audit; `Final Code/finalcode/live_wiring.py:9-33,36-80,83-116` supplies real capture, Bedrock extraction, CMS and SLB/triage. **FIRST** after CAPTURE (`document_text`, attachment name) or preferably EXTRACT (`ReferralFields` plus captured text held by `CaptureHolder`, `app.py:73-95`), before REVIEW. **MID** after REVIEW/GATE (`operator-edited fields`, completeness status), before CMS; or after CMS when the *resolved employer* is available (`orchestrator.py:107-122`), before SLB. **LAST** before SLB `subject_line(all_data)` (`:122-126`) / before live wiring completes triage (`live_wiring.py:109-116`). There is no Unity/assignment in this chain. Wrapping existing injected callbacks can place checks **inside** those callbacks (with explicit result/stop handling), but `on_stage` alone cannot put a first-class call *between* arbitrary stages with consistent state, outcome and audit. A proper Wizard stage/return handling requires a small orchestrator signature/state-machine extension; do not pretend it is plug-and-play.

**Standalone Unity** — `Processes/Unity/Stand-Alone/backend.py:235-279` validates manual/workbook input, starts worker, injects portal/record/notify/confirm/complete callbacks. `Processes/Unity/Deploy-Ready/unity_flow.py:35-53,67-127`: validate → attachment preflight → Unity assign portal → tracking log → iCaseManager approval prompt → RRS Complete Assignment. **FIRST** after validated manual inputs (customer/employer, claim, Special Instructions and optional selected attachment; no AI-extracted requested FCM) before `run_unity`; **MID** between portal work and tracking/approval, though at that point assignment work may already have started (too late for preventive R29); **LAST** before `run_unity`'s Assign button (`src/fcm_intake/legacy/legacy_unity.py:182-186`) and separately before `complete_assignment` (`unity_flow.py:107-125`). The controller's callbacks can be wrapped, but an internal pre-Assign seam inside the monolithic legacy portal routine needs refactoring or an explicit internal guard. Unity must stay standalone.

**Standalone SLB** — `Processes/SubjectLineBuilder/Deploy-Ready/manual_flow.py:43-84,99-143`: validate manual/Excel fields → open RRS builder → identity → claimant/like-items/provider/adjuster/attorney lookups with manual review → details → explicit final review → Create → optional triage/export. `Processes/SubjectLineBuilder/Stand-Alone/backend.py:108-172` manages worker and stale review IDs; `Processes/SubjectLineBuilder/Deploy-Ready/rrs_ui.py:563-587,756-772,873` fills requested NCM, creates and completes triage. **FIRST** after `validate` before RRS open (manual `customer`, `market`, `ncmContactName`, other fields; no captured referral text); **MID** after identity/lookups or before details (resolved UI selections may be seen by adapter, not generally in shared data); **LAST** at the existing final review before `adapter.create(data)` and separately before triage. For Final Code's SLB tail, `Processes/SubjectLineBuilder/Deploy-Ready/legacy_steps.py:3-77,823-849,1307-1325,2696-2700` skips capture/CMS when supplied, then fills Requested NCM and GAA and pauses before Create; a Wizard checking R29 must run *before the Requested NCM widget is filled*, not just at final Create review.

**Standalone Reopen-Check/CMS Customer Search** — `Processes/Reopen-Check/Stand-Alone/desktop.py:83-117,120-140` or pywebview `Processes/Reopen-Check/Stand-Alone/webview_app.py:147-248` validates manual/daily-workbook inputs and starts worker; `src/fcm_intake/workflows/reopen_flow.py:12-37` injects CMS functions into `Processes/Reopen-Check/Deploy-Ready/reopen_flow.py:8-56`: validate → case search → special open-TCM stop/visible-case confirmation → customer validation/selection → result. **FIRST** after input validation (unverified employer, claim, referral type), **MID** after case search/confirmation (case status, prior assignment, branch name where available through legacy reopen checker), **LAST** immediately after `check_customer` resolves name, before returning to caller. There is no generic pre-final-submit/assignment in this process; its last seam only guards customer handoff, not an RRS submission.

For rules applying FIRST/MID/LAST at any point, timing is a rule *declaration*, not a single global Wizard call. More than one invocation can occur for the same rule when new evidence arrives; record which context/version was evaluated.

## E. Customer-specific applicability

All eight owner-provided rules are Liberty Mutual carrier C02283; **do not equate the employer with that carrier**. At extraction, `AI/referral_schema.py:21-25,121-129,157-159` calls the printed `Customer Name` **Employer Name**, not insurer/carrier code; `Final Code/finalcode/cms_inputs.py:9-18` passes employer as CMS `customer`. `Final Code/finalcode/orchestrator.py:98-120` receives CMS's selected employer/customer name after case/customer checking and passes it downstream (`Final Code/finalcode/field_adapter.py:106-141`), but no C02283 code. `Processes/SubjectLineBuilder/Deploy-Ready/manual_flow.py:6-7,38-40` *defaults* the separate `market` to Liberty Mutual Commercial Market; `legacy_steps.py:849` writes that market into `tbCustomer`, while `:858` uses resolved employer in `tbEmployer`. These conventions might supply a **provisional** Liberty scope in a known-LM-only workflow, but a default is not verified identity and the model output is not a carrier code.

There is scattered customer/employer-specific branching, not a declarative policy registry: Goodyear/Cooper open-TCM stop (`Processes/Reopen-Check/Deploy-Ready/reopen_flow.py:28-38`), Goodyear/Texarkana GAA checkbox (`Processes/SubjectLineBuilder/Deploy-Ready/legacy_steps.py:1322-1325`), Continental/Michigan auto override (`:78-82`; `src/fcm_intake/legacy/legacy_unity.py:153-157`), Goodyear facility (`legacy_unity.py:1332-1429`), and hardcoded Liberty market/CMS selection (`src/fcm_intake/legacy/CMS.py:636-650`). `src/fcm_intake/legacy/legacy_cem.py:34,40-41,78` has a commented example C02283, empty `CUSTOMER_CODE`, and a hardcoded market choice during employer creation, not a per-run verified carrier-code field. Source searches for `C02283|customer_code|rule registry|Liberty Mutual` did not reveal a shared rule registry or a verified carrier identity in Final Code's result. Ask the owner what authoritative source attests C02283 for each run; delay binding an LM-only rule or mark its first-pass decision provisional until verified.

## F. Audit

`Final Code/finalcode/audit.py:46-106` explicitly whitelists per-run stage timestamps, captured/sent character counts, extracted/reviewed fields, completeness, CMS resolved customer, SLB status, outcome/reason and minimal error type/stage. `:143-156` redacts known secrets; `:159-202` atomically saves one JSON per run outside any Git tree. `Final Code/finalcode/app.py:185-223` calls `audit.stage` through `on_stage`, saves after the run, and treats audit-write errors as nonfatal. There is **no Wizard field now**; unknown `result['payloads']` keys are not automatically serialized. Recommendation: add an explicitly whitelisted `wizard_verdicts` array in `build_record` (bump `schema_version`) with `rule_id`, `timing`, `scope/verified carrier source`, `verdict` (`pass|flag|pause|not_applicable|uncertain`), minimal evidence location/field reference, actor/action, resolution/permission state and timestamps, plus stage timing for Wizard invocations. Avoid copying full referral passages, emails, branch messages, model prompt/response, secrets or free-form CMS payloads. A stopped/pending decision must still have an audit outcome; retention and human authorization record design remain owner decisions. Current audit records full extracted/reviewed field values, so any addition should be reviewed against its existing sensitive-data policy.

## G. Minimal recommendation (no implementation)

Create a small rule registry declaring `{id, timing: FIRST|MID|LAST, carrier_code, employer predicate, required inputs, evidence policy, candidate behaviour}`; allow the same rule to run at multiple stages when newly available evidence changes its status. At boundaries above, give a Wizard evaluator a sanitized context with captured-text access only where needed, extracted/reviewed fields, carrier-identity source and verification status, CMS result when available, prior verdicts and human authorization state. Require a typed response `{rule_id, applicability, verdict, evidence references, confidence/uncertainty, recommended action}`; deterministic validators own exact codes/identities and final gating, while an optional model only identifies ambiguous narrative/evidence. Keep a separate explicit human decision record rather than using a model's permission claim. Reuse workbench `notify`/`confirm` and pending review only for *attended* short-lived pauses; Unity and standalone processes have separate prompt bridges. Extend orchestration for explicit stops, resumption semantics and audit; do not smuggle the Wizard into `on_stage` or bypass existing gates. **Never** auto-award, choose a substitute FCM, assert customer permission, send branch/Liberty communications, decline or remove RRS referrals merely because an AI verdict says so. Owner has deferred which violations flag, pause or auto-correct.
