# W1 — Unity ↔ CMS Registration boundary (read-only, HEAD af3f83e)

**Conclusion: B — sequential but decoupled.** Registration needs the *persisted result* of Unity case creation and subsequent assignment/acceptance, but no Unity function calls the registration entry point, and the BRD explicitly transfers work after the referral leaves the prior inbox. It can be a separately launched module keyed to the verified claim/CMS case and the correct RRS referral row, not a direct continuation of the Unity browser session. This is an architectural inference, **not** a claim that the current legacy `CMS.run_case` is deploy-ready: it lacks the state and identity gates below and swallows failures. Sources: `Processes/Unity/Deploy-Ready/unity_flow.py:88-127`; `src/fcm_intake/legacy/CMS.py:2128-2167,947-1000,1843-1911`; BRD slides 94, 101–103, 120–123 (`docs/brd/09-advance-notice-and-assignment.md:15-23,100-111`; `docs/brd/10-cms-case-setup.md:25-43`; `docs/brd/11-complete-registration.md:11-52`).

## Safe independent-module input contract (proposal; INFERRED)

- **Required identity:** claim number; claimant full name normalized against the selected RRS referral; verified **CMS case ID** (from successfully completed Unity/RRS assignment if available, else a fresh lookup); Medical/Vocational **referral type**; uniquely identified **RRS registration referral/work item**, not `Claimant Row 0`. Tie all identities together against CMS case and current RRS row before mutation. Evidence for existing inputs/unsafe row assumption: `src/fcm_intake/legacy/CMS.py:947-1000,1850-1866,2128-2151`; BRD slides 99–103 (`docs/brd/09-advance-notice-and-assignment.md:72-108`; `docs/brd/10-cms-case-setup.md:25-43`).
- **Required state proof:** Unity task completed **and** CMS case materialized; Advance Notice/assignment or resolved exception; iCase accept (not reject); RRS option 19 with case ID successfully confirmed, Unity notification associated, state `UnityComplete`; supervisor's handoff to registration agent and registration referral visible/selected. A tracking INSERT is **not** sufficient proof because it can occur on failure (`Processes/Unity/Deploy-Ready/unity_flow.py:25-29,97-105`; BRD slides 94–101, `docs/brd/09-advance-notice-and-assignment.md:15-111`).
- **Required resources and policy:** explicitly injected CMS procedure connection setting (do not silently assume it equals tracking config), CMS account supplied through approved attended credential channel, available Unity lookup only for fallback, IE/Edge browser prerequisites, office/supervisor reference workbooks (filenames referenced by code, contents not inspected), RRS desktop window, and a verified CEM decision before choosing Reg Menu `3` vs `10`. `src/fcm_intake/legacy/CMS.py:40-43,112-126,289-307,925-943,1214-1218,1291-1296,1850-1883,1914-1965`; `src/fcm_intake/config.py:98-104`; BRD slides 108, 120, 122 (`docs/brd/10-cms-case-setup.md:108-120`; `docs/brd/11-complete-registration.md:11-20,33-41`).
- **Gate before Complete Reg:** re-read the selected RRS row's claimant, claim/case ID, referral type and status; assert all CMS tabs/attachment/notes/ERFS decisions complete, including human exceptions; pause if absent or ambiguous. Current code only compares claimant and swallows case failures (`src/fcm_intake/legacy/CMS.py:1843-1911`). BRD slides 117–120 (`docs/brd/10-cms-case-setup.md:237-265`; `docs/brd/11-complete-registration.md:11-20`).
