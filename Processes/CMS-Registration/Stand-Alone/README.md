# CMS Registration stand-alone

This is an **operator-started** step after Unity assignment and supervisor handoff, not the earlier CMS customer search in Final Code. The default run (`run.py`, `run.py --desktop` or the EXE) opens the attended **live** desktop against the configured CMS (UAT URLs in `config/local_settings.ini`). Scenarios, `--self-test` and `--desktop --offline` are synthetic and offline. No run automatically starts when the desktop opens.

From the repository root:

```text
.venv-bedrock/Scripts/python.exe Processes/CMS-Registration/Stand-Alone/run.py
.venv-bedrock/Scripts/python.exe Processes/CMS-Registration/Stand-Alone/run.py --scenario registered-cem
.venv-bedrock/Scripts/python.exe Processes/CMS-Registration/Stand-Alone/run.py --all-scenarios
.venv-bedrock/Scripts/python.exe Processes/CMS-Registration/Stand-Alone/run.py --self-test --report C:/Users/Administrator/AppData/Local/hermes/profiles/omniroute/cache/scratch/cms-reg/standalone-selftest.txt
.venv-bedrock/Scripts/python.exe -m unittest discover -s Processes/CMS-Registration/Stand-Alone -p "test_*.py"
```

To build only the frontend, run `npm ci` and `npm run build` in `Stand-Alone/frontend/`. Launch `run.py` (or `run.py --desktop`) for the attended live adapter, or `run.py --desktop --offline` for a synthetic operator window. **RRS data mode** requires **`FCM_RRS_DB_CONNECTION` explicitly for the registration stored-procedure lookup only**, read from the environment or external `.env`; there is **no fallback to `FCM_CMS_DB_CONNECTION`**. Excel data mode does not require either DB connection and never calls the RRS DATA lookup or daily CEM checker. The adapter retains the historical `cms_db_connection` argument name for the default RRS loader; the desktop passes an alternative in-memory `load_data(request, case)` callback for Excel. This callable is validated before browser creation and wholly replaces the default loader, without fallback. `FCM_CMS_REFERENCE_DIR` is optional (defaults to the repo `docs/` folder, which holds the office matrix). Missing setting **names** are shown before starting. Live mode shows a **CMS sign-in** card (username/password) in the window, prefilled from `FCM_CMS_USERNAME` / `FCM_CMS_PASSWORD` in the external `.env` like Reopen-Check; if left blank, sign-in is prompted after Start. The password is masked and the pair lives only in the worker's in-memory settings for that run. No credential is placed in UI state, result, scenario/report file or application logging. Avoid putting a real connection string into shell history.

Optional for **RRS data mode's default DATA loader**: `[cem] cem_log_path` in `config/local_settings.ini` (beside the EXE when frozen, repo `config/` in source mode) or env `FCM_CEM_LOG_PATH` names the CEM app's daily log `FCM CEM Checher.xlsx` (absolute path). When configured, that log is the sole CEM hint source instead of the legacy checker beside CMS.py; an unavailable file or missing today's sheet remains unknown and stops at `cem_status_unknown` for an explicit Yes/No, without legacy fallback. When unconfigured, the legacy daily checker remains. The adapter resolves this setting itself, but reads the hint lazily at DATA only. **Excel's supplied loader bypasses both CEM readers as well as the database**; its explicit/request CEM rules remain unchanged. Option 10 always requires operator confirmation. Details: [Deploy-Ready README](../Deploy-Ready/README.md#cem-routing-hint-fcm-11-126).

## Attended Excel setup source

Use `Processes\sample\CMS-Registration-Input.xlsx`, now based on the 69 columns in `AI-FCM-Output_50 Samples.xlsx` plus 13 CMS-specific columns, with five transferred referrals and their related provider/classification records. The AI source and original Subject Line input are unchanged; the previous CMS workbook was backed up. These populated files are sensitive local inputs and must not be committed. The shared `AI.cms_registration_excel` reader supplies both request fields and CMS setup data and still accepts the earlier Subject Line-based layout.

Required request columns are **Claim Number**, **First Name**, **Last Name**, **CMS - Referral type** (Medical/Vocational) and **CMS - CEM employer request** (yes/no when otherwise unknown). Unknown values are not fabricated during conversion; correct them in the workbook or applicable UI controls. CMS case ID and referral number are separate identifiers, not Claim ID or Record ID. Other setup fields may require operator review rather than being mandatory at Start.

1. **Open Excel** opens a native `.xlsx` picker. Loading a file does not start anything, select its first row, change RRS mode to Excel mode, or disable preview.
2. Choose a row explicitly, then **Load row**. This switches the active source to **Excel**, wholly replaces the request/setup payload (including blanks), and shows the file basename, row, warnings and editable setup controls before Start. Setup values and workbook content stay in session memory only.
3. Check missing values, referral type and CEM status. Original Subject Line categories do not imply Medical/Vocational; choose explicitly when blank. Unknown CEM stops at the existing `cem_status_unknown` gate unless the operator supplies yes/no. Unknown office stays blank; no claim-substring inference or RRS/daily-checker fallback is performed. Controlled office/supervisor reference workbooks and existing manual review gates remain required.
4. Correct the imported CMS setup fields before Start. Notes and instructions support multiple lines; provider types use a selection. Rows with multiple providers have separate provider controls instead of competing single-provider fields. For doctors, edit the full provider name or both doctor name parts: a full-name edit clears stale parts, while part edits update the name used for tab verification. Start rejects contradictory edited identities but preserves unchanged imported decorated names. Facilities use the provider name and hide unused doctor-part controls. Blanks explicitly clear values. The appointment date updates both setup and manual-review date. Changes survive status polling and a completed preview, but loading another row/workbook or choosing RRS resets them. Original source/reference values are read-only and do not become automated CMS fields. Existing manual gates and reference checks remain required.
5. Press **Start preview** separately, then review the selected CMS case and effective edited setup data. Those same edited values are supplied to CMS setup only in an explicitly authorized full run. Request referral-type corrections are used for setup; the original Excel type remains visible as review metadata. The request's explicit CEM choice takes precedence in both review and setup. Edits do not write back to the workbook.

Changing the claim or claimant identity after loading is rejected at Start; reload the correct row instead. Referral type, CEM status, optional CMS case ID and referral number may be corrected in the request. Opening a replacement workbook invalidates an active Excel row; it requires another explicit Load row, not a silent RRS switch. **Use RRS data** explicitly clears the imported setup/selection and resets the request, restoring the original manual-form + DB workflow. Data-source changes and imports are rejected while busy; picker/read results are also rejected if the source or run changed while they were pending. Start validates the edit allowlist and current workbook/row, then deep-copies the effective data under the state lock without changing the imported baseline.

The packaging recipe includes the shared reader, not populated input or restricted reference workbooks. These source changes do not rebuild an EXE or reload an already-running desktop. No live CMS, RRS, Bedrock or portal operation is established by offline tests.

After building the frontend, run `npx playwright test editable-setup.spec.ts --workers=1 --reporter=line` from `Stand-Alone\frontend` for synthetic single/multiple-provider edit, polling, row-reset and Start-payload checks in headless Edge. The test serves only the local build and injects a mock desktop bridge; it does not open a live application or portal.

**Live Start defaults to preview.** Leave **Stop before CMS setup (no changes or RRS submission)** checked. Preview may sign in, navigate/read CMS case candidates, load the selected RRS or Excel data source and request case/data review; approval then returns **stopped / preview_only** at REVIEW, before CMS_SETUP or COMPLETE_REG. It does **not** fill setup fields, save CMS changes, send emails or submit RRS registration. CMS tab postbacks may autosave, so filling fields and merely skipping the final Save is not a supported safe preview. Unchecking the option explicitly enables the normal write-capable registration sequence and requires separate owner authorization. Synthetic offline scenarios retain their existing behavior.

A lookup with no matching referral stops at DATA with **No matching registration referral was returned by the RRS lookup.** It does not fabricate data, change the input or try another database. Driver failures expose only fixed operation labels and SQLSTATE/exception class, never raw driver messages. Restart the source desktop after updating Python code (the running backend is cached); a frontend build alone does not reload it. These source changes do not update a previously built EXE.

The UI shows idle form → running stage/step progress → blocking case/data review with Approve or Cancel → distinct completed/stopped/cancelled/failed result. Ambiguous or unconfirmed cases list candidates; **Use this case** fills the CMS case ID for a *separate* operator Start, never launches automation. Live notify/confirm prompts block for operator acknowledgement. Do not close the window mid-run. Any partially completed live portal changes require manual inspection.

`--self-test` runs the 14 offline JSON scenarios and bridge smoke, writing a plain UTF-8 report; exit 0 requires every fixture's expected outcome/reason and smoke checks to pass. It does not prove the stored procedure schema, real CMS/Unity/RRS state, IE-in-Edge compatibility, portal persistence, CEM correctness, reference workbook versions or live registration. The packaged spec and `build.ps1` have been exercised offline: the build compiles the frontend in place, packages `dist/CMSRegistration.exe`, runs the frozen synthetic self-test, and writes `dist/CMSRegistration.exe.sha256`. The build defaults its report to the profile scratch directory; pass `-ReportPath` with a native absolute path to choose another. The spec does not embed restricted reference workbooks. The v1.0.0 binary passed packaged synthetic self-test in-repo and outside-repo; live deployment approval and portal validation remain pending.
